# Agent instructions for Protocol_E

## Selected assurance level

Formal proof relative to published theorems. Prove all project arguments and computational facts through the declared formal checking path. Permit only audited published-theorem assumptions and declared foundations. Independently audit target meanings, assumption translations and actual transitive dependencies. Do not require duplicate manual records for formal internal inferences.

## Start small

Read PROTOCOL.md and PROJECT.md. The selected protocol states the assurance requirements. These instructions organize the work without changing them. Initialize one canonical ledger alongside the first proof work. Begin with REVIEW_LEDGER.md or an existing adequate implementation; use a small script only for a concrete validation need.

Do not build a custom service, GitHub App, dashboard or general review engine unless requested or a demonstrated requirement cannot be met more simply. Do not turn an archive or hash update into a separate research project.

## Use meaningful units and one owner

Record a coherent lemma, application, construction or interface once. Give it stable identifiers and list its actual consumers. A checklist is a view of the evidence, not a requirement to restate the same proof many times. Group uses only when the same argument truly covers them.

Use one integrator and one selected candidate. Before assigning work, check for an active owner or an existing accepted result. If parallel work is authorized, assign bounded tasks with fixed inputs, disjoint output files and explicit acceptance criteria. Reviewers assess the exact delivered candidate. Do not spawn workers merely to repeat completed checks.

## Keep accepted work accepted

Bind review to mathematical statements, definitions, assumptions, proofs, source versions and consuming context. For a change, identify affected units and downstream uses. Reopen those units and the necessary composition checks. Preserve decisions on genuinely unaffected work.

A moved passage or changed line number usually needs a scoped binding update rather than a new mathematical derivation. A changed definition can invalidate an unchanged paragraph. Cache checks by their complete relevant inputs and checker version. Preserve earlier decisions; never replace their hashes to manufacture a fresh review.

## Keep trust and evidence honest

Apply the selected framework's trust boundary. For A through E, do not reprove published literature without a concrete reason beyond the required source, convention and applicability checks. For F, the entire mathematical dependency closure needs formal proofs, which may come from pinned libraries.

Every known substantive objection enters the ledger. Separate an invalid inference from an unperformed review, a source-access problem or an accepted repair awaiting incorporation. Report each at its actual scope. Do not declare completion from token counts, agent counts, file counts or an arbitrary percentage.

Record human and model review provenance honestly. Non-author review does not mean independent reasoning is guaranteed. If a reviewer writes a substantive repair, use a different reviewer when independent acceptance is required by the chosen protocol.

## Plan and rehearse the release

These operational checks preserve the selected protocol's assurance level. They add no mathematical review role, mandatory extra human, permission, or service.

Bind the primary release to an immutable commit and exact artifact hashes. Keep incidental hosting metadata, such as a workflow URL or displayed status, outside the identity of the material being reviewed. If a build or check consumes a generated merge commit, tree or other derived artifact, pin its exact identity as a stage input and invalidate affected checks when it changes. Check delivery state, freshness and authorization separately; do not omit security-relevant inputs from those checks. Do not redefine the primary candidate merely because a hosting service refreshed its metadata.

Before an expensive run, preflight the complete path from the selected inputs through validation, evidence assembly, publication and readback. Exercise the actual commands, schemas and consumers in a safe local rehearsal or supported dry run; identify any live-only checks still pending. Include missing, stale or malformed evidence, an interrupted stage, a failed publication and a retry after partial success. Where signed evidence already exists, check that the selected verifier accepts its exact historical formats, identities and trust configuration. Do not relabel, re-sign or rewrite old evidence to make a compatibility check pass. A mock transport does not establish live authentication or freshness.

Split expensive validation, evidence assembly and publication into independently resumable stages. Record each stage's complete relevant inputs, checker and configuration versions, output hashes and observed terminal result. Preserve successful stages when those bindings remain unchanged. If a relevant input or checker changes, invalidate and rerun the affected stage and its dependent checks; never reuse a success merely because filenames match. Before retrying a writer, check its actual process or remote job identity, terminal state and any completed side effects. Resume safely from that state instead of duplicating an action.

Assign one recovery owner. After two unexplained infrastructure failures in the same stage, diagnose the captured errors and reproduce the failing step at the smallest useful scope before another expensive full run. Continue independent proof, review or packaging work meanwhile. A retry must address the diagnosed cause or be justified by evidence that the external condition changed. Do not weaken a failed check or discard its evidence.

Give each phase an elapsed-time, compute and storage budget based on a measured sample or prior comparable run; label initial estimates. Report the current phase, job identity, elapsed time, last observed progress and exact error location without exposing secrets. Record actual phase costs and revise estimates as evidence arrives. Exceeding a budget calls for inspection and a recovery decision, not an arbitrary timeout that kills a possibly healthy job.

Prepare publication commands and destinations during preflight. After expensive validation passes, keep final publication short: check current bindings and authorization, transfer the exact validated artifacts, and read back the destination identity and required files. A delivery failure alone should not repeat unchanged expensive validation. Stop once the selected protocol's closure and release checks pass.

## Finish the specified task

State acceptance criteria before work. After they pass, finish the task. Reopen it for a changed premise, concrete finding or demonstrated omission, not because another review is possible. Do not recursively demand reviews of unchanged review prose.

Keep mathematical work, incorporation, and mechanical release work separate in status reports. Build the cumulative handoff once the research release is ready, then synchronize it with the manuscript, inventory, findings and artifact index. Do not rebuild every archive after every internal edit.

Tool failures need one recovery owner and bounded retries. Never replay a possibly live writer without checking its state. Preserve useful drafts and errors, and continue independent work when possible.

Existing user authorizations remain valid. Publication, external messaging, purchases and access changes still require the appropriate authorization. These templates grant none of them by themselves. Do not send credentials or unrelated private files to reviewers or release archives.
